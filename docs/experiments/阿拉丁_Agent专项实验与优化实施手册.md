# 阿拉丁 Agent 专项实验与优化实施手册

> **版本**：v1.0（2026-11-24）  
> **适用对象**：阿拉丁项目参与开发的工程师（你）与 Coding Agent（Claude Code / Codex 等）  
> **使用方法**：将本文档放到获授权的阿拉丁工作区，例如 `docs/experiments/agent-improvement-plan.md`；人与 Coding Agent 共同执行，按阶段更新证据。  
> **核心目标**：用阿拉丁**真实代码 + 可重复实验 + 可验证改动**，完成至少一项 Agent 工程优化闭环；建立后续可复用的评测、监控与回归机制。

---

## 0. 阅读指南与事实边界

本文是**执行计划，不是对阿拉丁现状的既成事实描述**。制定依据是目前已知的项目描述：阿拉丁是研发任务交付型多 Agent 平台，涉及 Task/Plan/Step/Validate、Server/Worker、ACP 对接 Coding Agent、上下文或 Memory 交接、代码产物与 PR；已有一定平台使用和相关代码，但实际功能边界、部署、指标、权限、问题是否存在，**均以仓库源码、配置、可运行环境和负责人确认结果为准**。

- **已经知道的动机**：2026-11-13 面试追问集中于平台观测、Token/时延/失败优化、个人贡献、任务编排与 Agent 评测。现在线上相对稳定、用户数量不多，不依赖等待生产故障；主动做质量基线、边界实验、可观测性补强和优化验证。
- **待验证的假设**：固定阈值压缩可能影响上下文质量；跨 Worker 交接可能丢失证据；Worker 中断可能导致迟到结果、重复副作用；计划完成不代表真实交付成功。这些**不是已发现的缺陷**。
- **个人贡献边界**：记录哪些代码由你亲自实现、哪些由 Coding Agent 生成并由你审查、哪些仅来自其他团队已有实现。不要将实验环境结果描述为线上改进，也不要将他人原有设计描述为自己实现。
- **数据边界**：仅在授权仓库和隔离环境运行。默认不导出真实用户 Prompt、内部源代码、密钥、客户数据、原始工具输出；Trace 使用元数据与脱敏摘要。

### 0.1 最终交付清单

必须尽量形成以下产物（文件路径可按项目调整）：

```text
experiments/
  README.md                           # 实验索引与运行方法
  inventory.md                        # 真实架构、埋点能力、源码证据
  questions.md                        # 问题假设和优先级
  dataset/                            # 脱敏/合成任务、验收规则、版本信息
  harness/                            # 运行器与测试适配器
  reports/
    baseline.md                       # 当前版本基线
    experiment-001.md                 # 首个对照实验
    regression.md                     # 回归报告
    interview-case.md                 # 面试案例（事实与贡献明确）
  evidence/                           # 脱敏日志、配置快照、trace refs、结果 CSV
```

**完成定义（DoD）**：至少一个可复现任务集、可运行 Harness、可信 Baseline、一项经过验证的变更（或证据充分的“无优化收益”结论）、相同任务条件的对照结果、源码/PR/测试记录、面试复盘。若没有获得更改权限，实验应明确标记为 `independent prototype` 而非 `merged production change`。

## 1. 工作组织：人与 Coding Agent 怎么分工

### 1.1 职责边界

| 工作 | 你（最终负责人） | Coding Agent（协作执行者） |
|---|---|---|
| 确定研究问题、判断业务价值 | 主责 | 提出备选假设并说明证据缺口 |
| 仓库与环境授权、敏感数据范围 | 主责、明确批准 | 绝不自行提升权限或上传数据 |
| 源码调查 | 核对关键调用路径 | 搜索、整理调用链、引用路径及行号 |
| 指标口径、测试设计 | 审批并解释取舍 | 起草规范、设计 Case、生成测试代码 |
| Baseline 运行 | 审核配置和预算 | 在授权环境按指令执行并保存结果 |
| 实验性改动 | 决定修改范围、Review | 小步提交补丁、单元测试、故障注入 |
| 结论及面试素材 | 对真实性负责 | 输出证据矩阵、反例和复盘初稿 |

**强制工作规则**：Coding Agent 应先调查再改代码；不得自动触碰生产配置、数据库写操作、推送远端、合并 MR、扩大权限、暴露秘密。变更优先在实验分支/Mock 环境。任何报告都要链接到可查的文件、函数、测试和运行结果。

### 1.2 Agent 操作守则（放在工作区 AGENTS.md / CLAUDE.md 的片段）

```md
你是阿拉丁专项实验的协作 Coding Agent。
目标是“证据驱动的真实改进”，不是制造漂亮指标或强行找到 Bug。
1. 先阅读 experiments/README.md 与 inventory.md；先列未知项，不得假设源码中有特定能力。
2. 每个架构结论必须附上文件路径、符号名、行号或测试证据。无法确认时明确写“未确认”。
3. 未获得明确批准前，不修改生产逻辑、不连接生产数据、不提交或推送远端。
4. 所有实验固定 git SHA、数据集版本、模型、工具、运行环境、预算和随机性配置；变化需记录。
5. 未拿到可靠 Token 统计时填 null/unknown，不能估算后当真实值。
6. 测试前先写预期、失败条件和停止条件；实验后记录失败与负面结果。
7. 产出小而可 review 的 diff，代码配测试，文档写出限制与个人贡献。
8. 如发现凭证/个人数据/内部源代码可能被外发，立即停止并报告。
9. 不得编造线上问题、用户规模、成本收益、PR 合入状态或个人职责。
```

### 1.3 每次会话的工作协议

1. **你给出明确任务**：研究范围、允许读/写目录、可运行环境、预算、禁止行为。
2. **Agent 先回复三项**：已知事实/未知项、计划执行的具体操作、潜在风险。
3. **你审批**：尤其是模型调用成本、测试数据访问、破坏性操作。
4. **Agent 执行并提供证据**：文件路径、命令、退出码、测试报告、结果文件。
5. **你验收/迭代**：只接受可复现结果；复杂改动分段 Review。

## 2. 四阶段总路线与决策门槛

| 阶段 | 建议投入 | 目标 | 必须通过的门槛 |
|---|---:|---|---|
| P0 源码与观测审计 | 1–3 天 | 知道阿拉丁实际做了什么、哪些数据可得 | 真实调用链、数据来源、权限和限制已经明确 |
| P1 最小评测基线 | 3–5 天 | 能稳定重复任务并判分 | 至少 10 个有效可运行 Case，结果和失败日志可追溯 |
| P2 一个重点优化实验 | 4–7 天 | 证实一项问题或改进空间 | Baseline 与 Treatment 可比，记录所有控制变量 |
| P3 回归、报告、面试案例 | 2–3 天 | 形成工程证据 | 结论、局限、代码证据和个人贡献清晰 |

时间为排期建议，不是保证；有模型成本、工具权限或环境阻碍时，应先做确定性 Mock 试验，**不跳过验收门槛**。第一轮以 2–3 周完成一个闭环为目标。

### 2.1 先做哪一项优化？

**先不要认定要优化 Token。** 用下面的选择矩阵给候选专项打分（每项 1–5 分）：

| 维度 | 权重 | 判断标准 |
|---|---:|---|
| 复现确定性 | 30% | 能否稳定构造失败/低效场景 |
| 可归因程度 | 25% | 能否区分模型、Worker、Server、工具、Git 的责任 |
| 自己可修改性 | 20% | 是否有权限且改动范围可控 |
| 结果可测量性 | 15% | 是否有清晰、可信的成功/成本指标 |
| 业务/面试相关性 | 10% | 是否对应真实研发任务和面试追问 |

初期候选：A. 上下文交接与工具输出；B. 任务恢复与迟到结果；C. Plan/Step/Validate 的结果验收；D. Git 合入验证。选得分最高且具备实验条件的一个，不同时做四个。

## 3. P0：阿拉丁源码审计（Coding Agent 第一轮任务）

### 3.1 必须回答的事实问题

**架构与职责**
- Task 创建、Plan 生成、Step 执行、Validate、终态更新各由哪些模块负责？
- Server/Worker/ACP 的实际通信方式、状态所有者、事件上报路径是什么？
- Memory 文件、摘要、历史消息、工具结果的读写/交接路径是什么？
- Agent/Worker 的模型调用是否经过网关？使用量是否来自 ACP、网关、客户端遥测？

**可观测性**
- Langfuse 目前在哪些位置埋点？Trace、Span/Observation、Session 和任务标识如何关联？
- 有没有可靠的 Task 级耗时、步骤状态、失败类型、Attempt、Worker 断连数据？
- 对 Token/成本：覆盖哪些模型和路径？累计值/增量值怎样区别？未知用量怎么表示？

**评测与结果判定**
- 完成 Step 的条件是 Agent 声称 done、通过测试、PR 存在，还是其他独立验证？
- 有没有现成自动化测试集、基准任务、CI、测试环境和运行记录？
- 是否已经有按任务类型统计结果的机制？

**可靠性**
- `attempt`、心跳、恢复、重试、幂等和终态约束是否存在？落在什么位置？
- Worker 断连时，本地 Agent 是否仍可能运行？结果如何回传？
- Git 分支/Commit SHA/合并结果的验证边界是什么？

## 4. P1：搭建最小可重复 Agent 评测 Harness

### 4.1 先定义评测对象和粒度

阿拉丁的评测要分三层；一开始优先做**结果层 + 执行可靠性层**，不要先追求一个复杂 LLM Judge。

| 层次 | 评测对象 | 优先判分手段 | 易踩坑 |
|---|---|---|---|
| 任务结果 | 需求是否被满足 | 单测/集成测试、构建、文件/接口断言、人工验收 | 不能拿 diff 与历史 PR 一样作为唯一成功标准 |
| 执行轨迹 | 规划、派发、工具、恢复是否合理 | 状态机断言、事件轨迹、角色/工具约束 | 工具成功 ≠ 工具选择正确 |
| 资源与效率 | 耗时、Token、成本、重试 | 统一运行记录与 Usage 口径 | 缺失 Token 不等于零，Span 嵌套时间不能直接相加 |

### 4.2 数据集构建规则

- **MVP**：10–20 条高质量可运行任务；后续扩展至 30–50 条。
- 类别建议：单文件修改、跨文件修改、测试修复、依赖/接口兼容、带日志故障的修复、需多 Step 协作的任务。
- 来源顺序：授权的历史需求 + 可用初始仓库/验收测试 > 项目内可复现 Issue > 自造合成任务。敏感数据必须脱敏。
- 每条 Case 必须固定初始 Commit 和工具/网络权限，并提供可执行的**成功判定**。
- 不可把历史 PR 原样放到 Agent 可见上下文中；它可作为参考或构建验收用，但不能污染提示。
- 若验收依赖主观质量，制定 Rubric 并保留人工双人复核样本；明确标记 Judge 的局限。

### 4.3 建议数据结构（示例 Schema，不强制字段名）

```yaml
case_id: codefix-001
version: v1
source_type: synthetic           # synthetic | sanitized_internal
repo_fixture: fixtures/sample-go-service
base_commit: "<fixed-commit-sha>"
task_prompt_file: prompts/codefix-001.md
allowed_tools: [read_file, edit_file, run_tests]
network_policy: deny
max_steps: 30
max_wall_seconds: 900
max_model_cost_usd: 2.00
expected:
  build_command: "go test ./..."
  test_command: "go test ./..."
  assertions:
    - "scripts/assert_case_001.sh"
  forbidden_changes:
    - "go.mod"              # 仅示例，实际按任务调整
labels: [go, bugfix, single-agent]
```

### 4.4 Harness 的最小闭环

```text
Dataset Case
   ↓
准备隔离 Workspace（固定 base_commit / 清理副作用）
   ↓
调用 Aladdin 测试接口（或经授权的 Adapter）
   ↓
记录 Task / Run / Attempt / Trace IDs
   ↓
等待终态（设总预算与超时）
   ↓
收集 Git 变更、测试产物、执行事件、Usage
   ↓
执行独立验证器（Build / Tests / Assertions）
   ↓
归档结果 JSONL/CSV + 脱敏 Trace 引用
```

**隔离与成本**：每次运行必须有独立工作目录/容器/分支；关闭生产写权限；限制网络、工具集合、运行时长、步数和成本。失败或中断必须清理 Workspace；不要在同一脏工作目录连续跑不同版本。

### 4.6 需要严格定义的指标

1. **任务成功率** = 验收通过的独立任务数 / 有效任务数；超时任务计失败并单独标注。报告样本量与任务类别。
2. **平台完成率** = Server 进入 `done` 终态的任务数 / 有效任务数；**不得代替任务成功率**。
3. **工具错误率** = 工具执行报错次数 / 所有有记录的工具调用次数；另统计错误是否导致任务失败。
4. **恢复成功率** = 故障注入后达到预期终态且状态/副作用断言通过的 Case 数 / 注入 Case 数。
5. **P50/P95 耗时** = Task 创建到终态的墙钟时间；并记录测试环境排队时间。样本少时 P95 只能作探索参考。
6. **Token/成本** = 同一任务的唯一模型调用 Usage 汇总；标明网关/ACP/估算来源、覆盖率和去重规则。不可靠时不报告“精确节省 X%”。
7. **失败归因** = 分层标记（模型输出、工具、编排、上下文、环境、验收不匹配、未知），允许 `unknown`，保留可核查 Trace。

### 4.7 可复现性控制

- 固定：数据集版本、仓库 base commit、阿拉丁 commit、模型与参数、工具定义、配置哈希、环境镜像、网络权限、验收器版本。
- 记录：温度/推理配置（能设置则固定）、执行日期、依赖服务版本、运行区域和模型服务可用性。
- 同一个 Case 可重复多次以观察波动；样本预算不足时明确报告不确定性。
- 实验分组**只改变一个主要变量**；如果修复涉及组合变更，应补充消融试验，无法做时说明局限。
- 不随意删除失败 Run；保留所有有效运行与剔除理由。

### 4.8 Agent Prompt 02：生成最小 Harness

> 基于已审查的 `experiments/inventory.md`，为阿拉丁开发**最小、隔离、可重复**的评测 Harness。先产出设计方案，明确调用现有接口的方式、测试 Workspace 隔离机制、退出/超时/成本限制、结果 JSON Schema、评分规则和清理策略。第一期只支持 10 个任务、确定性验收（构建、测试、文件断言），不要加入泛化 LLM Judge。请先创建 Mock 运行适配器与单元测试，确保无需真实模型也可测试 Harness；实际调用阿拉丁前让我确认。所有结果保留运行配置哈希、git SHA 和 Trace 引用。不要修改生产逻辑，不要连接生产数据。

## 5. P2 候选专项 A：上下文交接与工具输出优化（推荐第二步）

### 5.1 科学问题

> 在相同任务质量标准下，阿拉丁的平台层上下文组织与跨 Agent 交接是否存在可减少的无效 Token 或证据丢失？

**首要前提**：审查 Worker/ACP 与 Coding Agent 之间的上下文控制边界。平台可能只能控制共享 Memory/Step Summary，**无法控制 Claude Code 内部自动压缩与所有模型 Token**。如果不能插入底层工具输出路径，就把实验严格限定为**平台交接上下文优化**，不要宣称优化了底层模型用量。

### 5.2 假设与对照组

- H0：现有策略已合理；新策略不会在质量不下降的前提下降本。
- H1：对平台可控的共享上下文做结构化分层，比全部摘要或固定截断更能保留关键证据，可能降低重复回查或后续 Token。

| 组别 | 做法 | 备注 |
|---|---|---|
| A | 阿拉丁当前原始实现 | Baseline，不擅自改变 |
| B | 只调整压缩阈值/预算（若允许） | 单变量实验 |
| C | 结构化保留任务约束与执行状态；工具输出摘要 + 原文引用 | 需要可插入的上下文层 |

不要硬做三组；若无法安全实现 B 或 C，报告限制并选可行对照。

### 5.3 推荐数据集场景

- 长会话跨多个 Step（15+ 次工具调用）。
- 上下文中出现新的强制约束，后续 Agent 必须继续遵守。
- 大量相似日志，实际错误位于中间。
- 工具无显式 ERROR 但有非零退出码（如 OOM/137）。
- Planner→Developer→Tester 的 Memory 交接含未完成事项。
- 任务进行中重新规划，已有状态不可被旧摘要覆盖。

### 5.4 建议工程方案（作为候选，不预设原系统缺失）

1. **分层数据**：`task_constraints`、`step_state`、`recent_dialogue`、`summary`、`artifact_refs` 分离；关键状态结构化存储。
2. **原始证据保留**：超长输出存储在受控位置，返回 Artifact ID、摘要、内容哈希、行号范围；脱敏处理。
3. **信号提取**：根据退出码、错误标记、堆栈、首/末出现、重复签名整理证据；保留“未匹配错误但命令失败”。
4. **按需回查**：下游 Agent 有安全的按行号读取工具；设置回查次数与读取预算。
5. **预算隔离**：明确定义平台传输字节数、可控制的模型输入 Token、底层不可观测的 Token；三者不可混写。

### 5.5 关键指标与反例

- 验收通过率、任务约束保留率、关键错误召回率、引用可回查率。
- 可观测的模型 Token、单位任务成本及 Usage 覆盖率。
- 工具调用数、回查次数、任务耗时、压缩触发次数。
- **负面结果**：省 Token 但任务成功率下降；摘要导致关键错误丢失；回查次数激增；人工维护成本高。必须报告。

### 5.6 Agent Prompt 03A：上下文专项

## 6. P2 候选专项 B：长任务恢复与执行一致性（最易确定性验证）

### 6.1 科学问题

> Worker 断连、超时、Server 崩溃、结果迟到和重试发生时，是否会出现不合法状态推进、重复派发或外部副作用？

这类实验不需要大型 LLM 测试集，先用 Mock Worker 和控制时间/网络即可。

### 6.2 必查代码语义

- 执行身份：Task ID、Step ID、Attempt ID、Lease/Heartbeat。
- 当前执行权：如何更新、怎样确认仍然有效（CAS/条件更新等）。
- 迟到消息：是否携带 Attempt/Version，旧消息如何拒绝。
- 外部副作用：Git Commit/MR/文件写入等是否能判定已发生。
- 恢复位置：恢复原 Session、重建上下文，还是整个 Step 重跑。
- 终态：是否只允许合法状态转换、终态是否不可逆。

### 6.3 四个确定性故障注入用例

| Case | 注入点 | 正确性断言 |
|---|---|---|
| R1 | Worker 执行中停止心跳 | 按配置转移状态，任务可恢复或明确失败 |
| R2 | Attempt 2 完成后，Attempt 1 迟到上报 | 旧结果不能覆盖当前合法终态 |
| R3 | 工具副作用已完成，但 Server 未记录即崩溃 | 恢复时不得盲目重复不可幂等操作 |
| R4 | 同 Step 两个 Worker 同时回报完成 | 只有符合执行权和验证规则的结果可推进 |

**关键注意**：Fencing 只约束 Server 接受结果，不天然阻止旧 Worker 继续执行外部写入。对外部副作用还需隔离、幂等键、权限与补偿/人工审核。

### 6.4 指标与对照

- 违规状态更新次数：应为 0。
- 过期结果接受次数：应为 0。
- 非预期重复副作用次数：应为 0。
- 故障注入恢复成功率、恢复时长、重复派发次数。
- Baseline：当前版本；Treatment：必要的最小补丁；对相同故障脚本各重复多次。

### 6.5 Agent Prompt 03B：恢复专项

> 请审查阿拉丁 Task/Step/Attempt/Worker 心跳与终态更新链路，先给出状态机和关键路径的 `path:line` 证据。不要先宣称有竞态。编写 Mock Worker 故障注入：心跳超时、迟到结果、重复完成、外部写成功但持久化失败。要求测试记录旧/新 Attempt、状态转换、外部副作用。先运行当前版本获取 Baseline，发现可复现失败后才提出最小修复，且编写能防止回归的测试。若全部通过，输出已经成立的可靠性保障、尚未覆盖的故障与测试边界，不为了产生优化案例而修改代码。

## 7. 备选专项 C / D（仅当前两项不可行时展开）

### C. Plan → Step → Validate 的任务完成正确性

- **假设**：Agent 声称 `done` 但实际上未满足交付验收，可能触发错误推进。
- **用例**：无文件改动却返回 done、测试失败却返回 done、未满足依赖、工具失败但文本称成功。
- **实验**：Mock Agent 的输出与产物状态故意矛盾，检查 Step 是否只在独立验收通过后更新。
- **指标**：错误终态接受数、无效重试数、额外耗时、业务验收通过率。
- **优化候选**：产物/测试/Commit 验证与状态流转绑定；若已存在，补充边界测试即可。

### D. Git 合入验证的基线一致性

- **假设**：Agent 分支在旧目标分支上测试通过，但目标分支更新后，最终合并结果未经复验。
- **用例**：构造 A 基线→Agent 分支 B 测试成功→目标分支 C 修改依赖→merge(B,C) 失败。
- **实验**：隔离 Git Fixture，检查是否验证最终 Merge 产物，目标 HEAD 变化是否使验收失效。
- **指标**：未经有效验证的合入次数、重验次数、平均等待时间。
- **优化候选**：将验收与 merge commit SHA + 目标 HEAD 绑定；尽量复用 Git 服务端分支保护/合并队列。

## 8. 可观测性专项：为了实验而监控，不是先搭大盘

### 8.1 第一版必须串起来的事件

```text
TaskCreated -> PlanGenerated -> StepReady -> StepDispatched
  -> WorkerAccepted -> ACPStarted -> Tool/Model events (若可观测)
  -> StepFinished -> ValidationFinished -> TaskTerminal

其他事件：WorkerDisconnected / HeartbeatTimeout / RetryScheduled /
ResumeStarted / ContextCompacted / MemoryTransferred / ArtifactValidated
```

这些是目标事件名，实际可以映射阿拉丁已有事件。**不要为追求统一命名去重构业务代码**。

### 8.2 关联主键和字段

最小集合：`task_id`, `run_id`, `step_id`, `attempt_id`, `worker_id`, `agent_role`, `timestamp`, `status`, `error_class`, `duration_ms`, `trace_id`。上下文事件记录输入输出大小、artifact 引用与版本。模型用量事件额外记录 `model`, `usage_scope`, `usage_source`, `usage_complete`。

- Task ID/Run ID 是 Trace 与日志维度；**不要作为 Prometheus label** 造成高基数。
- 不同 Worker 需要透传相关 ID/trace context；不能自动关联时记录显式交接事件。
- 同一个模型调用从网关和 ACP 两边上报时，使用唯一调用 ID/来源去重，不重复计算成本。
- 累计 Session Usage 与单次 Usage 不得直接混加。没有可靠 Usage 就 `null`。
- 记录执行状态与**业务验收状态**两个维度，避免 Server `done` 被误报为业务成功。

### 8.3 首个可观测性验收标准

任给一个测试 `task_id`，能够找到：
1. Task 的起止时间、终态和验收结果；
2. 对应每个 Step/Attempt 的派发、完成、重试、失败；
3. Worker/ACP 关键过程或清楚标明不可观测范围；
4. 一处具体失败时可关联到日志/Trace/Artifact；
5. Token 是否可靠可得，以及来源。

### 8.4 Agent Prompt 04：最小埋点设计

### 9.1 先注册实验假设

每轮试验开始前写一页 `experiment-XXX.md`：

```md

- 固定变量：模型、提示、仓库状态、环境、工具、执行预算：
- 主指标（一个）：
- 护栏指标（验收成功率/安全断言/成本/耗时）：
- 成功标准：
- 停止条件：
- 成本预算：
- 执行命令：
- 结果文件：
```

### 9.2 不要被平均值骗了

- **可复现的正确性缺陷**：优先写确定性断言；例如旧 Attempt 覆盖终态发生 1 次就属于严重问题。
- **LLM 质量指标**：用同一批 Case 成对比较；随机性较高时重复运行，报告逐 Case 的胜负与波动，而不是仅凭 10 个任务宣称显著提升。
- **成本与时延**：同时报告均值、中位数、长尾和覆盖率；模型调用路径不一致时不可直接比较总 Token。
- **质量护栏**：不能只因省 Token 就通过；验收成功率/证据完整率不能出现不可接受的回退。
- **排除规则**：网络外部故障、环境初始化失败等必须预先定义，不能只剔除不利于新方案的数据。

### 9.3 严格避免的无效结论

- “稳定运行几个月” ≠ 恢复机制经故障注入验证。
- “Agent 返回完成” ≠ 需求验收通过。
- “Langfuse 看到 Trace” ≠ 有完整任务级可观测性。
- “固定阈值压缩” ≠ 平台 Token 一定减少。
- “工具调用成功” ≠ Agent 选对工具。
- “测试组成功率更高” ≠ 改动必然有效，尤其样本量小且模型非确定性。
- “Coding Agent 写出了补丁” ≠ 你独立实现；你要能审查、解释、验证并如实说明协作方式。

## 13. 风险与失败处理

| 风险 | 缓解措施 | 停止条件 |
|---|---|---|
| 真实代码、密钥、用户数据被上传 | 默认仅上报元数据、脱敏 Trace；限制外部模型访问 | 存在未经授权的数据外发可能性 |
| 实验破坏共享 Worker/任务 | 只在隔离测试环境，Mock 先行 | 影响其他人员任务或生产数据 |
| 模型调用费用失控 | 每 Case 限时、限步数、限成本 | 预算达到上限 |
| 因模型非确定性产生错误结论 | 成对实验、重复运行、记录配置 | 实验条件不一致且无法修复 |
| 找不到显著问题 | 换成边界验证与回归覆盖，不硬改 | 多轮无证据则终止该假设 |
| 修复未合入主仓 | 记录为实验补丁而非上线优化 | 无 Review 或无相应授权 |
